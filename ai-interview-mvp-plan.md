# AI interview taker — MVP plan (Phase 1)

## 1. Concept

A web app where a user selects a **subject**, **topic**, and **difficulty**, then takes a 5-question text-based interview. Questions are generated by an LLM, answers are scored and given feedback by an LLM, and a final results report is shown at the end.

---

## 2. Scope decisions

| Decision | Choice |
|---|---|
| Frontend | React |
| Backend | FastAPI |
| Question generation | LLM, generated dynamically (one at a time) |
| Scoring | LLM, returns score + feedback per answer |
| Questions per session | 5 |
| Interview flow | One question at a time (wait for answer before next) |
| Output format | Score (0-10) + detailed feedback per question + overall average |
| Storage | In-memory (no DB) for MVP |
| Subjects | Frontend, Backend |
| Topics (example) | React, JavaScript, CSS, Node.js, Databases |
| Difficulty | Easy, Medium, Hard |

---

## 3. Out of scope (Phase 1)

- Coding / code-execution questions
- User authentication / accounts
- Persistent database storage
- Voice input
- Subtopic-level granularity
- Editing/retrying previous answers

---

## 4. User flow

```
[1. Setup screen]
   - Select Subject (Frontend / Backend)
   - Select Topic (React / JS / CSS / Node / DB)
   - Select Difficulty (Easy / Medium / Hard)
   - Click "Start interview"
        |
        v
[2. Interview screen]  <-- loops 5 times -->
   - Shows Question (N of 5) + progress bar
   - User types answer in textarea
   - Click "Submit answer"
   - (loading state: "Scoring...")
   - Backend scores answer + generates next question
        |
        v  (after question 5)
[3. Results screen]
   - Overall score (average / 10)
   - Per-question breakdown: question, score, feedback
   - "Start new interview" button -> back to Setup screen
```

| Element | Type | Notes |
|---|---|---|

## 6. API contract (FastAPI)

| Endpoint | Method | Request body | Response |
|---|---|---|---|
| `/start-interview` | POST | `{ subject, topic, difficulty }` | `{ session_id, question, question_number, total_questions }` |
| `/submit-answer` | POST | `{ session_id, answer }` | `{ score, feedback, done: bool, next_question? , question_number, total_questions }` |
| `/results/{session_id}` | GET | — | `{ subject, topic, difficulty, overall_score, questions: [{ question, answer, score, feedback }] }` |

**Session state (in-memory dict, keyed by session_id):**
```
{
  subject, topic, difficulty,
  current_index,
  qa_log: [ { question, answer, score, feedback } ]
}
```

**LLM prompt 1 — generate next question**
- Input: subject, topic, difficulty, list of previously asked questions (to avoid repeats)
- Output: plain text question

**LLM prompt 2 — score answer**
- Input: question, user's answer, difficulty
- Output: strict JSON — `{ "score": <0-10 int>, "feedback": "<string>" }`
- Note: difficulty can also affect scoring strictness (Hard = stricter grading), not just question complexity — decide and document this in the prompt.

## 7. Build order (target: 1–2 hours)

| Step | Time | Task |
|---|---|---|
| 1 | 15 min | FastAPI skeleton with all 3 endpoints, hardcoded/mock responses (no LLM) |
| 2 | 20 min | React skeleton — 3 screens, routing/state, wired to mock backend |
| 3 | 30 min | Plug in real LLM calls for question generation + scoring |
| 4 | 20 min | Prompt tuning — ensure scoring JSON output parses reliably |
| 5 | 15 min | Styling pass + edge cases (empty answer, last question) |
| 6 | 20 min | End-to-end test run, bug fixes |

## 8. Open question to resolve before/during build

Should difficulty also affect **scoring strictness** (Hard questions graded more rigorously) or only affect **question complexity** while scoring stays consistent? Recommendation: bake difficulty into the scoring prompt so it does both — simpler to implement as one prompt variable.
